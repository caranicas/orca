# Orca Discord Integration

## Functional & Technical Specification

**Status:** Ready for architecture discovery and implementation  
**Objective:** Provide a fully functional Discord interface for managing Orca projects, workspaces, and agent sessions remotely, particularly from mobile devices.

---

## 1. Overview

Build a bidirectional Discord integration for Orca that allows users to manage projects, interact with agents, receive notifications, and approve actions without needing to use the Orca mobile application.

Discord is an alternative interface to Orca, not an independent agent runtime.

**Core principle:** Orca remains the source of truth for projects, workspaces, sessions, agent execution, and conversation history.

### Primary Goals

1. Provide one Discord text channel per Orca project.
2. Represent Orca workspaces and agent sessions as Discord threads.
3. Allow direct, bidirectional communication with existing agent sessions.
4. Provide actionable notifications for questions, blockers, failures, approvals, and completions.
5. Support basic project, workspace, and session management through Discord.
6. Keep routine tool execution and verbose logs out of Discord by default.
7. Maintain reliable synchronization between Discord and Orca.
8. Preserve Orca's existing behavior and architecture.

### Non-Goals

- Replacing Orca's desktop application.
- Reimplementing agent orchestration.
- Maintaining independent Discord conversation histories.
- Streaming every tool invocation by default.
- Automatically publishing agent-generated content.
- Creating a separate agent execution engine.

## 2. Discord Organization

### 2.1 Project Channels

Each Orca project maps to a dedicated Discord text channel.

Example:

```text
ORCA
├── #minecraft-civilization
│   ├── World Generation [Workspace]
│   ├── Terrain Agent [Session]
│   ├── Character Development [Session]
│   └── Episode Pipeline [Session]
│
├── #card-auction-bot
│   ├── Auction Scraper [Workspace]
│   └── Image Verification [Session]
│
└── #orca-control
```

Project channels serve as the primary entry point for project-level commands and status information.

### 2.2 Workspace Threads

Each Orca workspace may have a persistent Discord thread.

Workspace threads support:

- Workspace-level conversation and coordination.
- Workspace status summaries.
- Listing active sessions.
- Creating new agent sessions.
- Viewing blockers and outstanding approvals.

### 2.3 Agent Session Threads

Each Orca agent session maps to a Discord thread.

Messages sent to the thread must be routed to the exact corresponding Orca session.

Responses generated by that session must return to the same Discord thread.

Multiple sessions belonging to the same workspace must remain independently addressable.

### 2.4 Discord Thread Limitations

Discord does not support nested threads.

Workspace and agent-session threads must therefore be siblings under their project channel.

The relationship between a workspace and its sessions must be maintained through persistent identifiers and optionally reflected in thread naming, introductory messages, or pinned messages.

Thread names must never be used as the authoritative routing key.

## 3. Bidirectional Messaging

### 3.1 Discord to Orca

When a user sends a message in an agent-session thread:

1. Identify the Discord thread.
2. Resolve its corresponding Orca session.
3. Verify authorization.
4. Submit the message through Orca's existing session interface.
5. Preserve session context and continuity.
6. Deliver the resulting agent response back to the originating thread.

Messages must resume the existing session rather than inadvertently creating a new one.

### 3.2 Orca to Discord

When an agent produces a user-facing message:

1. Identify the originating session.
2. Resolve its Discord thread.
3. Classify the event.
4. Apply the configured notification policy.
5. Deliver the message to Discord when appropriate.

The integration must support messages originating from both the desktop interface and Discord.

### 3.3 Message Deduplication

Messages must not be duplicated when Discord-originated input is reflected back through Orca's event system.

Use message IDs, correlation IDs, or equivalent identifiers to prevent loops and duplicate delivery.

### 3.4 Conversation Ordering

Preserve message ordering within each session where practical.

Concurrent sessions must not block one another.

---

## 4. Notification System

### 4.1 Default Behavior

Discord should display meaningful, actionable agent communications rather than a continuous stream of execution logs.

**Default notifications include:**

- Agent questions requiring user input.
- Approval requests.
- Blockers requiring intervention.
- Agent failures.
- Session completion summaries.
- Meaningful user-facing agent responses.

**Default notifications exclude:**

- Routine tool invocations.
- Raw terminal output.
- Intermediate execution details.
- Debug logging.
- Internal reasoning.
- Repetitive progress events.

Internal reasoning must not be exposed through Discord, including in verbose mode.

### 4.2 Notification Levels

Support three configurable modes.

**Quiet**

Only approvals, blockers, failures, and questions requiring user action.

**Normal — Default**

Quiet notifications plus meaningful agent responses and completion summaries.

**Verbose**

Normal notifications plus available tool execution summaries, progress events, and diagnostic output that is safe to expose.

Verbose mode must not reveal secrets, credentials, hidden reasoning, or sensitive environment variables.

### 4.3 Notification Configuration

Allow notification levels to be configured per session.

Project-level defaults may be added after the initial implementation.

### 4.4 Direct Navigation

Notifications should appear in the originating session thread whenever possible.

If an aggregated notification is posted elsewhere, it should include a direct link to the relevant thread.

## 5. Commands

Initial command interface:

| Command            | Purpose                                            |
| ------------------ | -------------------------------------------------- |
| `/orca status`     | Display Orca runtime status                        |
| `/orca projects`   | List available projects                            |
| `/orca workspaces` | List workspaces for the current project            |
| `/orca sessions`   | List sessions for the current workspace or project |
| `/orca start`      | Start a new session                                |
| `/orca stop`       | Stop an active session                             |
| `/orca resume`     | Resume an existing session                         |
| `/orca inbox`      | Show items requiring user attention                |
| `/orca verbose`    | Change session notification level                  |
| `/orca help`       | Display supported commands                         |

Commands should use Discord's native slash-command interface.

Use autocomplete and structured choices where supported.

Do not assume all commands can be implemented using existing Orca APIs. Verify available capabilities during architecture discovery.

## 6. Approval Workflow

Agents may request user authorization before performing certain actions.

Discord must support actionable approval messages.

Example:

**Terrain Agent — Approval Required**

The agent wants to modify the terrain generation configuration.

Actions:

- Approve
- Reject
- View details

Requirements:

1. Approval requests must be associated with the exact originating session and action.
2. Only authorized Discord users may approve or reject.
3. Requests must have unique identifiers.
4. Duplicate submissions must not execute an action twice.
5. Expired or already-resolved approvals must be handled gracefully.
6. Approval state must be reflected in Orca.
7. Discord must not bypass Orca's existing permission or approval mechanisms.

If Orca does not expose an approval interface, document the limitation and propose the smallest safe integration change.

---

## 7. Session Lifecycle

### Session Creation

When a new Orca session is created, automatically create its corresponding Discord thread when project synchronization is enabled.

### Active Sessions

Active sessions remain addressable through their Discord threads.

### Completed Sessions

Completed sessions should receive a completion summary.

Their threads may be archived according to configuration.

### Resuming Sessions

If Orca supports resuming a completed session, the integration should reopen or reuse its Discord thread.

### Deleted Sessions

When a session is deleted, preserve or archive its Discord thread according to retention policy.

Do not silently recreate a deleted Orca session when a user replies to an old thread.

### Restart Recovery

The integration must recover project, workspace, session, and thread mappings after restarting.

## 8. Persistent Mapping

Maintain stable relationships between Orca entities and Discord resources.

Suggested logical schema:

```text
ProjectMapping
- orcaProjectId
- discordGuildId
- discordChannelId
- createdAt
- updatedAt

WorkspaceMapping
- orcaWorkspaceId
- orcaProjectId
- discordThreadId
- createdAt
- updatedAt

SessionMapping
- orcaSessionId
- orcaWorkspaceId
- orcaProjectId
- discordThreadId
- notificationLevel
- lastProcessedEventId
- createdAt
- updatedAt

ApprovalMapping
- orcaApprovalId
- orcaSessionId
- discordMessageId
- status
- createdAt
- resolvedAt
```

These are conceptual models, not prescribed database tables.

Use the persistence technology already established in Orca where appropriate.

Mappings must support reconciliation after crashes, network interruptions, and restarts.

## 9. Technical Architecture

```text
Discord
   |
   | Discord Gateway / Interactions
   v
Discord Integration Service
   |
   ├── Authentication & Authorization
   ├── Command Router
   ├── Message Router
   ├── Notification Filter
   ├── Approval Handler
   ├── Mapping Store
   └── Event Delivery
   |
   | Existing Orca Interfaces
   v
Orca
   |
   ├── Projects
   ├── Workspaces
   ├── Sessions
   ├── Agent Runtime
   └── Approval System
```

### Implementation Preferences

- TypeScript.
- Discord.js or another well-maintained Discord library.
- Reuse existing Orca infrastructure.
- Prefer a separate integration service when practical.
- Minimize changes to Orca's core runtime.
- Use event subscriptions where available.
- Avoid polling when reliable event delivery is already supported.

These preferences are subject to the repository's actual architecture.

## 10. Security

### Authentication

Use a dedicated Discord bot token.

Store credentials in environment variables or Orca's existing secret-management system.

Never commit credentials to source control.

### Authorization

Restrict control to explicitly authorized Discord users and guilds.

Discord channel visibility alone must not grant execution permissions.

### Command Permissions

Potentially destructive commands must require appropriate authorization.

### Approval Permissions

Approval interactions must validate the acting user's identity and the originating request.

### Secret Protection

Sanitize logs and notifications.

Do not forward credentials, environment variables, API keys, or sensitive terminal output.

### Network Access

Prefer authenticated local or private communication between the Discord bridge and Orca.

Do not expose unauthenticated Orca control endpoints to the public internet.

---

## 11. Reliability

The integration must handle:

- Discord connection interruptions.
- Orca runtime restarts.
- Discord bot restarts.
- Missing or archived threads.
- Deleted Discord channels.
- Session termination during message delivery.
- Duplicate events.
- Concurrent session activity.
- Discord API rate limits.
- Temporary message delivery failures.

Use bounded retries with backoff where appropriate.

Persist sufficient state to recover from restarts.

Avoid creating duplicate Discord threads during reconciliation.

Suggested configuration:

```env
ORCA_DISCORD_ENABLED=true
DISCORD_BOT_TOKEN=
DISCORD_GUILD_ID=
DISCORD_ALLOWED_USER_IDS=
DISCORD_DEFAULT_NOTIFICATION_LEVEL=normal
```

Actual configuration should follow existing Orca conventions.

Do not expose bot tokens in client-side application code.

## 13. User Experience

### Project Channel

The user can:

- Ask for project status.
- List workspaces.
- Find active sessions.
- Start work.
- Review outstanding issues.

### Workspace Thread

The user can:

- Review workspace status.
- List associated sessions.
- Start a new session.
- Give workspace-level instructions where supported.

### Agent Session Thread

The user can:

- Send a direct message to the agent.
- Receive meaningful agent responses.
- Answer questions.
- Approve or reject actions.
- Change notification verbosity.
- Resume or stop the session.

### Inbox

The inbox aggregates:

- Pending approvals.
- Unanswered agent questions.
- Blocked sessions.
- Failed sessions.

Each item should link to its originating thread.

## 14. Implementation Phases

### Phase 0 — Architecture Discovery

Inspect Orca's repository and identify the actual project, workspace, session, messaging, event, and approval interfaces.

Produce a brief technical findings document.

### Phase 1 — Working Vertical Slice

Implement:

1. Discord bot connection.
2. Project-channel association.
3. Session-thread association.
4. Discord-to-Orca message delivery.
5. Orca-to-Discord response delivery.

Verify that an existing Orca session can be controlled from Discord.

### Phase 2 — Automatic Synchronization

Add automatic project, workspace, and session discovery.

Implement thread creation and persistent mappings.

### Phase 3 — Notification Filtering

Implement quiet, normal, and verbose modes.

Add completion summaries and failure notifications.

### Phase 4 — Commands and Approvals

Implement session management, inbox, and approval interactions.

### Phase 5 — Reliability and Polish

Add recovery, reconciliation, retry handling, documentation, configuration, and comprehensive tests.

## 15. Acceptance Criteria

1. A Discord project channel maps to exactly one Orca project within the configured guild.
2. Workspace threads map to the correct Orca workspaces.
3. Session threads map to the correct Orca sessions.
4. Sending a Discord message resumes the intended existing session.
5. Agent responses return to the correct Discord thread.
6. Desktop-originated agent responses can be delivered to Discord.
7. Routine tool output is excluded in normal mode.
8. Questions, blockers, failures, approvals, and completion summaries are delivered.
9. Verbose mode can be configured per session.
10. Restarting the bridge preserves existing mappings and avoids duplicate threads.
11. Unauthorized Discord users cannot control Orca sessions or approve actions.
12. Existing Orca desktop functionality continues to work without regression.

---

## 16. Definition of Done

The integration is complete when a user can manage an existing Orca agent session entirely through Discord, receive actionable notifications, respond to questions, approve supported actions, and resume the conversation without opening the Orca mobile application.

All behavior must be grounded in Orca's actual supported interfaces, with any required core changes documented and tested.
